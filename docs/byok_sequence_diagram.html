Fluxo de Segurança BYOK

Arquitetura de criptografia reversível no servidor e blindagem de API Keys no banco de dados do Estagionauta.

sequenceDiagram
    autonumber
    actor Usuário

    participant Back as Backend Hono (Cloud Run)

    Note over Usuário,Front: Registro da Chave
    Usuário->>Front: Insere API Key

    Note over Back: Criptografa chave com AES-256-GCM

    Back->>DB: Salva ciphertext + IV no perfil do usuário
    DB-->>Back: Sucesso
    Back-->>Front: Confirmação de salvamento (sem retornar a chave)

    Note over Usuário,Front: Execução de Pergunta/Simulação
    Usuário->>Front: Executa simulação ou mensagem do Rover
    Front->>Back: POST /api/simulator/start
    Back->>DB: Carrega perfil do usuário
    DB-->>Back: Retorna dados + chaves criptografadas
    alt Chave própria existe
        Note over Back: Descriptografa chave em memória
        Back->>AI: Chamada de API com a chave do Usuário
        Note over Back: Consumo de Crédito = 0

        Note over Back: Consome 1 crédito local (consume_credits)
    end
    AI-->>Back: Resposta da IA
    Back-->>Front: Resposta formatada

Pontos-Chave de Segurança

🔑 Blindagem Unidirecional

Depois de salva no banco, a chave de API torna-se estritamente irrecuperável para o cliente. O frontend só recebe confirmações booleanas (ex: hasGeminiKey: true). Sem rotas de leitura, um ataque XSS no navegador nunca conseguirá roubar a chave.

🔒 Criptografia AES-256-GCM

O backend Hono encripta a API Key antes de persistir no banco. Mesmo que o Supabase seja comprometido, as chaves permanecem seguras, pois a chave mestra (BYOK_ENCRYPTION_KEY) existe apenas no ambiente isolado do Cloud Run.
