O Nascimento do Rover: Como a IA Agentic vai Engolir os Formulários Estáticos (e como as plataformas de recrutamento podem evoluir)

Por Paul Pessoa (Fundador do Estagionauta)

A experiência de buscar vagas de emprego ou de estágio na internet virou sinônimo de burocracia. Quem nunca teve que preencher dezenas de campos de formulário idênticos logo após fazer o upload do currículo em PDF e ver as informações virem corrompidas?

🚀 Validação do Futuro da UX (O Caso do LinkedIn Premium)

Recentemente, enquanto eu navegava no LinkedIn, recebi uma notificação do assistente de IA deles perguntando: "Quer triplicar suas chances enviando mensagens diretas com nosso assistente?". Ao clicar em "Yes, show me!", o sistema me redirecionou sozinho para a página de empregos e disparou outra pergunta de fluxo: "Help me find it.". Ao interagir, a aba de chat se expandiu, realizando uma navegação guiada e inteligente de telas. Percebi que eu estava construindo exatamente a mesma lógica conversacional no Estagionauta com o Rover! A maior rede profissional do mundo está validando que a navegação ativa guiada por agentes é o futuro.

No Estagionauta, decidimos que os nossos usuários não deveriam passar por isso. Em vez de forçar o preenchimento de campos manuais rígidos, criamos o Rover: um copiloto inteligente e autônomo incorporado diretamente na interface do produto que ajuda o estudante a criar, preencher e gerenciar seu perfil conversando.

O Paradigma do Agente Autônomo (ReAct) vs Chatbots Tradicionais

A grande maioria das integrações de Inteligência Artificial que vemos no mercado resume-se a chatbots passivos, ou seja, interfaces de chat que apenas respondem perguntas baseadas em textos estáticos. Eles conversam, mas não tomam nenhuma ação no sistema.

O Rover foi projetado sob a arquitetura de Agentes Autônomos ReAct (Reason + Action). Ele não é um mero gerador de texto. Ele é integrado ao ecossistema do aplicativo por meio de um loop de chamadas de funções (Tool Calling) de baixa latência utilizando a infraestrutura do Groq (modelos Llama) e OpenAI.

Quando você conversa com o Rover no painel lateral do app, ele segue um ciclo contínuo:

  • Pensar: O agente avalia a mensagem do usuário e decide se precisa buscar ou alterar algum dado no sistema.
  • Agir: Ele seleciona a ferramenta adequada na API do backend (como ler dados do perfil ou salvar uma nova experiência).
  • Observar: O backend executa a função localmente, interage com o banco de dados e devolve o resultado para o modelo.
  • Responder: O modelo analisa a resposta da execução e responde ao usuário em linguagem simples.

Orientação Espacial e Sitemap

Um dos maiores desafios de agentes de IA em sistemas SaaS é a falta de contexto sobre onde o usuário está navegando. Resolvemos isso injetando o mapa completo de rotas do site (como /perfil, /candidaturas, /gerador-curriculos) diretamente no prompt de sistema do Rover.

Isso confere ao agente a capacidade de orientar o usuário ativamente, enviando links das telas certas:

"Notei que você quer alterar sua formação. Você pode editar os dados diretamente no seu perfil clicando em /perfil ou simplesmente me dizer o nome da faculdade que eu atualizo para você agora mesmo."

Estrutura do Projeto (Monorepo)

Para garantir que essa comunicação acontecesse sem latências, estruturamos o Estagionauta como um monorepo simples:

Estrutura de Diretórios 
estagionauta/
├── src/          (Frontend em Vite + React + Tailwind CSS)
├── api/          (Backend Hono.js em Node.js)
├── shared/       (Tipagens compartilhadas entre front e back)
└── supabase/     (Migrações SQL e configurações do banco de dados)

Essa estrutura nos permite compartilhar tipos em TypeScript entre a API e a interface, além de centralizar a geração de esquemas do banco.

O Rover por Dentro: A Anatomia das Ferramentas (Tooling)

O Rover tem acesso a 5 ferramentas principais no backend que permitem a manipulação de estado e leitura de contexto do estudante:

  • check_profile: Consulta as informações cadastradas no perfil do usuário, como nome, contatos, experiências profissionais, formação acadêmica e links.
  • update_profile: Permite que a IA altere os dados do perfil do usuário (escrevendo informações no banco) com base no que o usuário pediu na conversa.
  • check_credits: Verifica o saldo de créditos disponíveis do usuário para rodar simulações ou análises.
  • calculate_recess: Executa as fórmulas matemáticas locais para calcular o período de recesso (férias) remunerado do estagiário.
  • analyze_resume: Realiza a leitura e a análise estruturada do currículo enviado pelo usuário.

Como as ferramentas são declaradas para a IA

No Hono.js, descrevemos as ferramentas para o modelo utilizando esquemas JSON. Abaixo está um exemplo simplificado de como definimos a ferramenta de atualização de perfil no backend para que a IA saiba como e quando chamá-la:

updateProfileDefinition.ts 
// Exemplo de definição de ferramenta passada para o modelo de linguagem
export const updateProfileDefinition = {
  type: 'function',
  function: {
    name: 'update_profile',
    description: 'Atualiza o perfil do estudante no banco de dados. Use esta ferramenta quando o usuário solicitar alterações em suas experiências, formação acadêmica, competências ou links.',
    parameters: {
      type: 'object',
      properties: {
        city_state: { type: 'string', description: 'Cidade e Estado onde reside' },
        portfolio_url: { type: 'string', description: 'Link do portfólio' },
        github_url: { type: 'string', description: 'Link do GitHub' },
        bio: { type: 'string', description: 'Breve descrição profissional' },
        education: {
          type: 'array',
          items: {
            type: 'object',
            properties: {
              institution: { type: 'string' },
              degree: { type: 'string' },
              fieldOfStudy: { type: 'string' },
              startDate: { type: 'string' },
              endDate: { type: 'string' },
              current: { type: 'boolean' }
            }
          }
        }
      }
    }
  }
};

Exemplos de Diálogos e Mutações de Estado

Para entender a diferença prática entre um chatbot comum e um agente, veja dois cenários de conversas reais extraídos do Rover:

Diálogo 1: Atualização de Perfil

  • 👤 Usuário: "Adicione que fiz um curso de extensão em Node.js de março a junho de 2025 na faculdade SENAC."
  • ⚙️ Rover (Internamente):
    1. Analisa a frase e identifica a intenção de modificar dados acadêmicos.
    2. Aciona a ferramenta update_profile com o payload: { education: [{ institution: 'SENAC', degree: 'Extensão', fieldOfStudy: 'Node.js', startDate: '2025-03', endDate: '2025-06', current: false }] }.
    3. A API do Hono executa o UPDATE no Supabase.
    4. O banco retorna sucesso.
  • 🤖 Rover (Para o usuário): "Pronto! Já adicionei o curso de extensão em Node.js no SENAC ao seu perfil profissional. Você pode conferir a alteração atualizada lá na sua tela de perfil."

Diálogo 2: Cálculo e Regras de Negócio

  • 👤 Usuário: "Comecei meu estágio em 10/01/2025 e recebo uma bolsa de 1200 reais. Quantos dias de férias eu tenho direito hoje?"
  • ⚙️ Rover (Internamente):
    1. Identifica a necessidade de calcular recesso de estágio.
    2. Executa a ferramenta calculate_recess com os parâmetros { startDate: '2025-01-10', endDate: '2026-06-02', stipend: 1200 } (utilizando a data atual como ponto de parada).
    3. A função calcula a diferença de meses, aplica a proporção da Lei do Estágio (30 dias para cada 12 meses) e calcula o valor financeiro do recesso.
  • 🤖 Rover (Para o usuário): "Como você está estagiando há aproximadamente 17 meses, você já acumulou o direito a 42 dias de recesso remunerado. Caso você tire esses dias em dinheiro, o valor proporcional a receber é de aproximadamente 1.680 reais."

A IA além do RAG tradicional: Tool-Use Database Mutation

Muitos desenvolvedores associam IA em documentos apenas ao RAG tradicional (Retrieval-Augmented Generation). Mas há uma grande diferença entre o RAG comum e a arquitetura de Tool-Use que aplicamos aqui:

Diagrama Mermaid: RAG vs Tool-Use 
graph TD
    subgraph RAG Tradicional - Somente Leitura
        R1[Pergunta do Usuário] --> R2[Busca Vetorial em Docs]
        R2 --> R3[Injeta Contexto no Prompt]
        R3 --> R4[LLM gera Resposta de texto]
    end
    subgraph Agentic Tool-Use - Leitura e Escrita
        A1[Comando do Usuário] --> A2[LLM decide usar Ferramenta]
        A2 --> A3[Executa Função localmente no Banco]
        A3 --> A4[Altera Estado / Escreve no Supabase]
        A4 --> A5[LLM confirma Ação e Sincroniza Frontend]
    end

No RAG tradicional, a IA apenas lê fragmentos de documentos para responder perguntas. Não há alteração de estado.

No nosso modelo de Tool-Use, a IA atua como uma interface de leitura e escrita. Ela consulta informações estruturadas do banco, processa a lógica e executa mutações (escreve novos dados) na base do Supabase. O usuário não precisa preencher o formulário; ele dá a instrução, a IA valida as regras e altera a tabela.

Como as Plataformas de Recrutamento Podem Evoluir (Gupy, Solides, LinkedIn)

Muitas plataformas de recrutamento no mercado são criticadas por criarem funis burocráticos e frios para os candidatos. Não se trata de criticar por criticar, mas de propor um novo modelo de interações. Como essas ferramentas podem migrar de coletores estáticos de dados para assessores ativos de carreira?

  • UX Conversacional para Candidatos: Em vez de preencher formulários rígidos, o candidato conversaria com um assistente. O assistente analisaria o PDF do currículo, preencheria as informações iniciais e tiraria dúvidas em tempo real: "Identifiquei que você colocou Node.js no currículo, mas não mencionou no seu perfil. Qual framework você utilizou? Posso atualizar seu cadastro?".
  • Buscas Semânticas para Recrutadores: Recrutadores perdem muito tempo configurando buscas rígidas de palavras-chave. Com um agente inteligente, a busca passa a ser contextual: "Preciso de estagiários em Olinda com perfil voltado para backend que demonstrem boa escrita e estejam matriculados no ensino superior". O agente faz o cruzamento semântico e entrega os perfis mais aderentes.

Nossas Escolhas de Engenharia

Para manter essa estrutura rodando com o menor custo e complexidade, tomamos decisões muito claras:

React & Hono.js

Optamos pelo React no frontend por sua componentização declarativa e pelo Hono.js no backend por ser extremamente leve, TypeScript-first e projetado para baixa latência. Como o fluxo do agente exige chamadas sequenciais entre o modelo e as funções locais, cada milissegundo economizado na API melhora drasticamente a fluidez da conversa.

Fetch Nativo do Node.js

Evitamos bibliotecas pesadas como Axios. Com o Node.js 18+, a API de fetch nativa tornou-se robusta e estável. Usá-la reduz as dependências do container do backend, otimizando o tempo de inicialização a frio (cold start) do servidor.

A Stack de Deploy: Custo Zero que Escala

  • Vercel (Frontend): Hospeda o frontend estático com CDN global, cache inteligente e HTTPS automático, garantindo carregamento instantâneo para o usuário.
  • Google Cloud Run (Backend): A API Hono.js roda dockerizada no Cloud Run. Escolhemos essa infraestrutura pela sua capacidade de Scale-to-Zero. Se não houver tráfego ativo, o container desliga e o custo é zero. Quando uma chamada chega, ele liga em segundos, escalando automaticamente caso o tráfego exploda. Um trade-off de leve cold start inicial para ter custo base de R$ 0.
  • Supabase (Banco, Auth & RLS): Centraliza nosso banco de dados relacional PostgreSQL, gerenciamento de autenticação por JWT e uploads de arquivos (Storage), com políticas rigorosas de Row Level Security (RLS) para proteção nativa dos dados do estudante.
  • Brevo (Envio de E-mail): Canal seguro de envio de e-mails transacionais (como o envio do PDF do currículo). O serviço roda estritamente no backend, protegendo as chaves de API.
  • Registro.br (Domínio): Gerencia as conexões DNS do domínio profissional estagionauta.com.br com apontamento limpo e seguro para os servidores da Vercel e do Cloud Run.

Padrão BYOK (Bring Your Own Key) e Diferenciação de LLMs

Ao implementar as conexões de inteligência artificial, adotamos uma estratégia inteligente de distribuição de modelos baseada em custo e velocidade:

  • Groq API (Llama 3): Utilizada no loop ReAct principal e Tool Calling. A Groq fornece velocidades incríveis de inferência (centenas de tokens por segundo), reduzindo o tempo de espera do chat para níveis imperceptíveis. Sem a velocidade da Groq, o loop de ferramentas de um agente ReAct tornaria o chat cansativo e inutilizável.
  • OpenAI API (GPT-4 / TTS): Reservada para tarefas que exigem alto nível semântico e capacidade analítica complexa, como a análise profunda estruturada de currículos ou síntese de voz (TTS) ultra-realista para simulação de entrevistas de membros premium (enquanto membros gratuitos utilizam a síntese de voz nativa do próprio navegador).

Frontend: UI & React Hooks

A interface (Vite + React) gerencia o estado da aplicação de forma declarativa. Para a comunicação com o backend, os componentes utilizam custom hooks do React Query que interagem com o apiClient.ts. Esse cliente centralizado é responsável por injetar dinamicamente o cabeçalho Authorization: Bearer [JWT] utilizando a sessão de autenticação ativa do Supabase.

Backend: Hono.js Layered Architecture

A API Hono.js recebe as requisições de forma estruturada: as rotas validam o payload usando Zod (garantindo consistência sintática antes do processamento). O middleware de autenticação decodifica o token JWT com o Supabase e expõe o usuário no contexto da requisição. Por fim, a camada de serviços executa lógica pesada de terceiros (como sessões de checkout no Stripe, inferência da OpenAI e persistência no PostgreSQL).

Shared: Ponte e Contrato Estrito

O diretório /shared/types é o coração contratual do monorepo. Todos os tipos em TypeScript (planos, status de simulação e históricos de transações) são definidos de forma centralizada e compartilhada. Se a API de backend mudar a estrutura de retorno de uma ferramenta do Rover, o frontend é impedido de compilar no build do Vite até que o contrato seja satisfeito em ambas as pontas.

O que é o Rover?

O Rover é um agente autônomo baseado no padrão ReAct para ler e alterar o banco de dados via chamadas de API, dispensando os tradicionais formulários estáticos de preenchimento.
